# ABC Controller - 技術架構總覽

本文件旨在闡述 ABC 平衡車控制系統的設計理念、技術演進與核心架構。系統採用分層設計，將複雜的平衡控制任務解構為控制、感知、執行與應用四個層次，並建立在 ESP32 雙核 FreeRTOS 即時多工框架之上。

## 1. 控制層 (Control Layer)

控制層是平衡車的大腦，負責所有姿態解算與運動控制。其核心是一個精密設計的**三層串級 PID 控制器**，它將不穩定的二階系統（單擺模型）轉化為穩定、可控的運動平台。

### 核心控制架構：三層串級 PID

我們的架構從單環 PID 演進而來，最終沉澱為一個由「速度環」、「直立環」與「馬達環」組成的三層串級 PID 系統，並輔以一個獨立的「轉向環」。系統支援多層級的運作模式（`MODE_STOP` → `MODE_FREE` → `MODE_PWM` → `MODE_MOTOR` → `MODE_ANGLE` → `MODE_VELOCITY` → `MODE_REMOTE`），各環路依據當前模式選擇性啟動。

- **外環 - 速度環 (Velocity Loop)**
- **目標**：控制車體前後移動的速度。
- **輸入**：遙控指令或腳本設定的「目標速度」與馬達編碼器回饋的「目前速度」。
- **輸出**：一個微小的「目標俯仰角 (Target Pitch)」。為了向前加速，此迴路會命令車體向前傾斜一個小角度，反之亦然。
- **運行頻率**：以 `OUTER_LOOP_DIVIDER=4` 分頻運行，約為主迴路的 1/4（50Hz），確保外環只在穩定的低頻段發出溫和指令。

- **中環 - 直立環 (Angle/Balance Loop)**
- **目標**：維持車體的絕對姿態平衡，是整個系統的穩定基石。
- **輸入**：速度環輸出的「目標俯仰角」與 IMU 感測器回傳的「實際俯仰角」。
- **輸出**：一個核心的「平衡控制量」（最終轉換為目標馬達 RPM）。
- **運行頻率**：200Hz，與主控制迴路同步，以最高頻率對抗重力擾動。

- **內環 - 馬達環 (Motor RPM Loop)**
- **目標**：精確驅動馬達，確保其實際轉速嚴格跟隨上層指令。
- **輸入**：直立環與轉向環混合後計算出的「目標 RPM」。
- **輸出**：精確的 PWM 訊號，直接驅動馬達硬體。

- **並行環 - 轉向環 (Steer Loop)**
- **目標**：控制車體的轉向速度與方向。
- **輸入**：遙控指令的「目標轉向量」與左右輪 RPM 差值。
- **輸出**：一個「轉向控制量」，它會與直立環的輸出混合，以差速方式施加在左右輪上。
- **命名統一**：原 `yaw` 已統一重命名為 `steer`（`7d8a6e2`），更準確地反映其為「轉向控制」而非「偏航角控制」的本質。

### 關鍵技術演進 (詳細說明)

- **`38cb865` - PID 的誕生：從開環到閉環**
    此提報是控制思想的起點。它首次在 `Processing_Motor` 模組中引入了 `motor_pid`，標誌著系統從簡單地「發送指令」（開環 PWM）進化到「發送指令並根據回饋修正」（閉環）的全新階段。雖然此時僅應用於馬達層，但它為整個專案引入了 PID 控制演算法和回饋控制的核心理念，是後續所有複雜控制策略的基石。

- **`e9c5ef6` - 架構的躍遷：串級控制 (Cascade Control)**
    這是專案在控制架構上最重要的一次躍遷。該提報明確地以「集中式串級控制」為目標，創建了 `AppMode` 模組。它將 `38cb865` 引入的 PID 概念從單一的馬達控制，提升到了真正的「平衡策略」層面，即透過建立內外環的嵌套結構（直立環控制姿態，速度環控制運動），將原本耦合的「平衡」和「移動」兩大難題成功解耦。可以說，這個提報標誌著平衡車「大腦」的正式誕生。

- **`9f5ae51` - 控制的精煉：引入陀螺儀阻尼**
    此提報引入了一項專業級的優化技術。為了解決高頻震盪，我們不再單純依賴 PID 的微分(D)項來處理誤差的變化率，而是在計算直立環輸出時，直接將感測器回傳的「真實俯仰角速度」(`current_gyro_x`)作為一個獨立參數送入 PID 控制器。這個純淨、即時的角速度數據，為系統提供了極其強大而精準的動態阻尼，使其能像安裝了電子避震器一樣，快速抑制外部衝擊和內部震動，獲得更「硬朗」的平衡姿態。

- **`9f5ae51` - 體驗的優化：指令濾波**
    同一次提報中，我們將低通濾波器(LPF)的應用位置，從「感測器量測端」遷移到了「使用者指令端」。過濾感測器數據會讓控制器對真實世界的反應變慢，產生延遲感。而僅對使用者的目標指令（如目標速度）進行濾波，既能讓車體的加減速過程變得平滑，提升「操控感」，又不犧牲控制器對外部干擾（如地面顛簸）的快速反應能力。這是一次將「使用者體驗」與「核心穩定性」分離處理的精妙改進。

- **`dbd96be` - 結構的解耦：速度環與直立環分頻**
    此提報將速度環與直立環的執行頻率正式解耦。透過引入 `OUTER_LOOP_DIVIDER`，速度環以 1/4 的頻率運行（50Hz），而直立環仍以 200Hz 的全速運行。這避免了低速外環的溫和指令被高速內環過度放大的問題，同時也在軟體架構上明確了「慢控制」與「快控制」的分工，提升了整體穩定性。同時修正了轉向輸出的限幅邏輯，確保偏航指令始終可控。

- **`cd6768e` - 狀態的乾淨切換：模式切換時重置控制器**
    此提報確保了每次模式切換時，所有 PID 控制器的積分器、濾波器和中間變數都會被清零。這解決了從一個模式切換到另一個模式時，殘留的積分飽和 (Integral Windup) 或歷史狀態導致的「初始衝擊」問題，使每次模式過渡更加平滑和安全。

- **`7d8a6e2` & `befcb4a` - 命名與邏輯的精煉：Yaw → Steer**
    這兩次提交統一將控制路徑中的 `yaw` 命名重構為 `steer`，使其語義更貼切——平衡車的轉向並非控制「偏航角」，而是控制「左右輪差速」。同時移除了遙控模式中基於速度的轉向靈敏度縮放，簡化了轉向邏輯，確保在低速和高速下都有一致的轉向手感。

### 重要設計資產 (解決方案)

1. **串級架構分離了問題域**：
    - **資產說明**：一個由「速度環 -> 直立環 -> 馬達環」組成的嵌套式控制結構。外環（速度）的輸出是內環（直立）的目標，內環的輸出又是最內環（馬達）的目標。
    - **解決問題**：它根本性地解決了單一控制器「目標衝突」的問題。一個試圖同時「維持平衡」和「移動到某點」的單 PID，其參數必定是衝突的，極易導致震盪。
    - **技術價值**：此架構將問題分離。**直立環**可以被調校得極其「激進」，以 200Hz 的頻率專注對抗重力，維持姿態。**速度環**則可被調校得相對「平緩」，以 50Hz 發出溫和的運動指令。這種職責分離是實現高性能平衡控制的正規且最穩定的方案。

2. **基於角速度的動態阻尼**：
    - **資產說明**：在直立環 PID 計算中，除了角度誤差，還直接引入了來自陀螺儀的「即時角速度」(`current_gyro_x`)作為前饋或阻尼項。
    - **解決問題**：解決了平衡車對外部衝擊反應遲鈍、以及在靜止時容易產生高頻抖動的問題。標準 PID 的 D 項（微分）計算的是「誤差的變化率」，訊號不夠純淨且反應不夠直接。
    - **技術價值**：即時角速度是一個極其乾淨且強烈的訊號，它直接反映了車體的運動趨勢。將其引入控制，相當於為系統增加了一個與角速度成正比的「反向力矩」。車體傾倒越快，抵抗力就越強。這如同一個反應迅捷的電子避震器，能有效吸收和抑制各種擾動，是車體姿態「穩如泰山」的關鍵。

3. **依賴於感知層的穩定姿態**：
    - **資產說明**：控制層的穩定性，高度依賴於感知層提供的、經過 AHRS 演算法融合後的、無長期漂移的絕對角度。
    - **解決問題**：若沒有穩定的角度參考，控制層的「零點」會不斷漂移，導致車體在靜止時也會緩慢移動，無法真正站穩。
    - **技術價值**：一個穩定可靠的「垂直參考系」是所有平衡控制的基礎。控制層透過信任感知層提供的數據，得以專注於控制策略本身，而不必處理感測器融合的複雜性。

4. **依賴於執行層的精確響應**：
    - **資產說明**：控制層的效能，建立在執行層能精確實現其 RPM 指令的基礎上。
    - **解決問題**：若馬達無法精確執行轉速指令（例如因電壓或負載變化），控制層的計算輸出將變得毫無意義，整個串級控制將會崩潰。
    - **技術價值**：一個可靠的執行層，為控制層提供了一個「所見即所得」的承諾。控制層下達「500 RPM」的指令，執行層就確保實現「500 RPM」的轉速。這個可靠的契約是整個控制系統得以有效運作的前提。

5. **FreeRTOS 指令佇列 (Command Queue)**：
    - **資產說明**：`AppMode` 透過 FreeRTOS `xQueue` 接收來自不同任務（遙控器、序列埠腳本）的指令，以執行緒安全的方式解耦指令發送者與控制迴路。
    - **解決問題**：在 FreeRTOS 多核多工環境下，若搖桿任務（Core 0）直接呼叫控制任務（Core 1）的函式，將引發資料競爭和不可預期的行為。
    - **技術價值**：佇列機制確保了跨核通訊的安全性。`enqueue_mode()` 和 `enqueue_target()` 任何任務均可安全呼叫，控制迴路則在每次 `update()` 開頭統一處理佇列中的指令（`process_command_queue()`），實現了生產者-消費者模式下的「無鎖」安全互動。

## 2. 感知層 (Sensing Layer)

感知層是系統的感官，負責將物理世界的動態轉化為精確的數位訊號，為控制層提供決策依據。

### 核心架構：IMU + CPF 互補濾波融合解算

感知層的核心是 `CPF` (Complementary Position Filter) 模組，一個基於 DCM（方向餘弦矩陣）的高性能姿態融合算法。它取代了早期簡易的互補濾波，以 DCM 矩陣旋轉方程為骨架，結合了自適應加速度計校正與線上陀螺儀偏差估計，提供了在全姿態範圍內穩定且精確的歐拉角輸出。

### 關鍵技術演進 (詳細說明)

- **`ea276a0` - 感知的起點：整合 MPU6050**
    這是感知層的創世紀。在此之前，系統對外部世界一無所知。這次提交整合了 MPU6050 感測器的驅動程式庫，讓主控板首次能透過 I2C 協議讀取到原始的加速度和角速度數據。儘管數據原始且充滿噪聲，但它為系統打開了感知物理世界的大門。

- **`1cbb4b5` & `38cb865` - AHRS 的導入與重構：從數據到資訊**
    原始的感測器數據並不能直接用於平衡控制。這兩次提交實現了從「原始數據」到「有效資訊」的關鍵轉化。`1cbb4b5` 初步引入了 AHRS 姿態解算演算法，對陀螺儀數據進行積分，以獲得姿態角。隨後的 `38cb865` 則將其從 C 語言風格的程式碼重構成為一個獨立的 C++ 類別 `Processing_AHRS`，並引入了互補濾波等更成熟的演算法，開始融合加速度計數據來修正陀螺儀的長期漂移。這標誌著感知層「大腦」的形成。

- **`05f1b1e` - 精度的關鍵一步：校準與穩定**
    此提交解決了業餘級 IMU 感測器的一個核心痛點：製造誤差導致的靜態偏移(Bias)。我們在系統啟動流程中加入了一個自動校準程序：系統靜置數秒，測量此時感測器的靜態輸出，並將其作為「零點」偏移量在後續所有計算中減去。此舉極大地提升了姿態解算的絕對精度，確保車體能準確辨識何為「水平」。同時，新增的啟動穩定階段，也確保了濾波演算法在主控制開始前有足夠的時間收斂到一個穩定值。

- **`c1eba78` - AHRS 的進階：濾波加速度融合與快速閘控**
    此提交對 AHRS 算法進行了重要的迭代優化。改為使用**濾波後的**加速度計數據進行姿態融合，降低了瞬態振動對融合結果的影響。同時引入了「快速閘控 (Fast Gating)」機制：當加速度計讀數偏離重力加速度 1g 過多時，果斷地將加速度計的融合權重降為零，避免在高動態機動（如急停或撞擊）下引入錯誤的姿態修正。

- **`3076700` - 感知的深化：向心加速度補償**
    這是感知層一次具有專業深度的提升。當平衡車轉彎時，IMU 感測器會承受向心加速度，這會污染加速度計的讀數，使融合算法誤以為重力方向發生了偏移。此提交在 `hal_CPF.cpp` 中引入了基於槓桿臂 (`lever_arm`) 和角速度的**向心加速度補償** (`ω × (ω × r)`)，從量測的加速度中扣除這個「假性重力」分量，使得融合算法在動態轉彎時仍能維持高精度的姿態估計。同時，IMU 的濾波帶寬也被適度提升，以獲取更即時的動態響應。

- **`80e4e57` - 初始化的魯棒性：統計檢定與重初始化**
    此提交強化了 CPF 模組的初始化流程。系統不再盲目信任啟動時收集的陀螺儀數據，而是對收集窗口內的數據進行**變異數統計檢定**。若檢測到數據的變異程度超過閾值（代表機體在收集期間受到了擾動），系統會自動丟棄這批數據並重新開始收集，直到獲得一組真正靜態、可信的校準數據。這極大地提升了上電初始化的可靠性，避免了「因開機時手部抖動而導致偏差校準失敗」的問題。

### 重要設計資產

1. **DCM 互補濾波算法 (CPF)**：
    - **資產說明**：一套位於 `hal_CPF` 模組內、基於方向餘弦矩陣的姿態融合算法。它以 DCM 矩陣的旋轉微分方程進行陀螺儀積分（預測），以加速度計重力向量與 DCM 預測重力向量的叉積誤差進行校正（更新），並同步在線估計陀螺儀偏差。
    - **解決問題**：它同時解決了兩個單一感測器的致命缺陷：1）陀螺儀積分產生的**長期漂移**；2）加速度計在動態運動中受到的**線性加速度干擾**。
    - **技術價值**：相較於簡易的互補濾波，DCM 方法**無奇異點問題**（避免了萬向節鎖），且其自適應權重機制（`check_acc` 閘控 + 大角度 `angle_confidence` 衰減）使其在靜止時精度高、在動態和大角度傾斜時不會被干擾。加上在線陀螺儀偏差估計（`bias_omg` 更新），系統能自動適應溫度漂移等長期變化，是整個平衡系統長時間穩定運作的基石。

2. **啟動時自動校準 (Auto-Calibration) 與統計檢定**：
    - **資產說明**：在系統啟動初期，CPF 進入一個專用的初始化階段 (`Phase 1`)。它持續收集 `LC_WINDOW_SEC`（3 秒）的陀螺儀數據，計算其均值作為偏差，並**計算變異數進行靜態條件檢定**。只有當變異數低於閾值時，才接受此次校準結果。
    - **解決問題**：消費級 MEMS 感測器因製造工藝和溫度影響，每次上電的「零點」讀數都不同。此外，操作者在開機時可能無意間晃動車體，導致校準數據受到污染。
    - **技術價值**：此資產確保了每次運行的**初始基準都是準確的**。統計檢定機制加上自動重試，讓系統不依賴操作者的配合即能獲得可靠的初始偏差估計，極大地提升了系統的可靠性和「傻瓜式」用戶體驗。

3. **處理層的高度抽象 (`prs_ahrs`)**：
    - **資產說明**：`prs_ahrs` 模組將所有與感測器相關的複雜操作（I2C通訊、暫存器讀寫、數據融合、校準流程）全部封裝起來，僅向上層提供一個極其簡單的 `get_ahrs_data()` 介面。
    - **解決問題**：避免了上層模組（如 `AppMode`）需要了解和處理底層硬體細節和複雜數學，造成了職責不清和程式碼污染。
    - **技術價值**：這是「關注點分離」原則的完美體現。它讓控制層的開發者可以專注於思考控制演算法，腦中所想的單位是「角度」和「角速度」，而非「暫存器位址」和「原始ADC讀值」。這讓上層程式碼更清晰、更健壯，也更易於維護。

## 3. 執行層 (Actuation Layer)

執行層是系統的四肢，負責將控制層的抽象指令（如「轉速 500」）精確無誤地轉化為物理世界的運動。

### 核心架構：HAL + Processing 雙層驅動

執行層採用嚴格的雙層架構：底層 `hal_motor` 負責 GPIO/PWM 電氣操作與 PCNT 硬體計數器讀取，上層 `prs_motor` 建構在 HAL 之上，實現 RPM 閉環 PID 控制與濾波邏輯。此架構使得硬體替換只需修改 HAL 層，上層控制邏輯零修改。

### 關鍵技術演進 (詳細說明)

- **`38cb865` - 閉環的萌芽：引入馬達 PID**
    這是執行層從「啞巴」到「會思考」的決定性一步。透過整合編碼器的訊號回饋，並在 `Processing_Motor` 模組中首次引入 `motor_pid`，執行層不再僅僅是個開環的「指令傳達者」（按指令輸出 PWM），而是進化成一個能主動修正誤差的閉環系統。它開始思考「我的實際轉速是否達到了目標？如果沒有，我該如何調整？」，從而奠定了整個三層串級控制最內環的基礎。

- **`3939671` - 架構的成熟：模組化與持久化**
    這次大規模重構將馬達控制模組的職責完全固化，使其成為一個更加獨立、健壯的一等公民。更重要的是，它透過整合 `ConfigStore`，賦予了馬達環 PID 參數的「記憶」能力。這不僅僅是為了方便，更是一種理念的體現：承認底層馬達的精確控制與上層的平衡演算法同等重要，其調校成果同樣是寶貴的資產，需要被持久化保存。

- **`14cb829` - 控制的精細化：濾波與平順**
    此提交專注於提升馬達運轉的品質。從編碼器直接讀取的 RPM 數據可能存在因測量周期或硬體抖動引起的「毛刺」，這些噪聲會讓馬達 PID 產生不必要的微調，導致額外的震動和噪音。透過對 RPM 量測值增加濾波器，為馬達 PID 提供了更平滑、乾淨的輸入訊號，使其輸出也更為穩定，最終提升了整個系統的運轉平順性和靜音效果。

### 重要設計資產

1. **馬達 RPM 閉環控制**：
    - **資產說明**：`prs_motor` 模組透過讀取馬達編碼器的訊號來計算「實際轉速」，並將其與「目標轉速」進行比較，利用一個獨立的 PID 控制器動態調整 PWM 輸出來消除誤差。
    - **解決問題**：解決了開環 PWM 控制的「不確定性」。開環控制下，50% 的 PWM 輸出不等於 50% 的最大速度，它會因電池電壓下降、負載變化（上坡/下坡）、摩擦力改變而劇烈波動。
    - **技術價值**：此閉環設計將不確定的馬達變成了**可預測、可信賴的致動器**。它向上層提供了一個穩固的「履約承諾」：無論負載、電壓如何變化，只要你命令我轉到 500 RPM，我就會盡力做到 500 RPM。這是整個串級控制能夠成立的根本前提。

2. **分層抽象設計 (HAL + Processing)**：
    - **資產說明**：一個兩層式的軟體結構。底層 `hal_motor` 負責與具體的驅動晶片打交道，實現最基礎的電氣控制。上層 `prs_motor` 則基於 HAL，實現 RPM 計算、PID 等更高級的邏輯。
    - **解決問題**：避免了高層邏輯與特定硬體的強耦合，提高了程式碼的可維護性和可移植性。
    - **技術價值**：若未來硬體升級，更換了不同型號的馬達驅動晶片，我們**只需修改 `hal_motor.cpp`** 的內部實現即可，而 `prs_motor` 乃至整個 `AppMode` 的程式碼一行都不用改。這體現了優秀的軟體工程思想，為專案的長期演進提供了極大的靈活性。

3. **直觀的物理量介面 (`set_target_rpms`)**：
    - **資產說明**：執行層向上層提供的公開介面，其單位是具有明確物理意義的「每分鐘轉速 (RPM)」，而非底層的電氣單位「PWM 占空比」。
    - **解決問題**：將上層開發人員從繁瑣的底層細節中解放出來，避免了在演算法中進行心算轉換。
    - **技術價值**：它允許控制層的開發者在**問題的領域**（物理世界）中思考，而不是在**解決方案的領域**（電子世界）中思考。這讓控制演算法的設計和閱讀都變得極其直觀，從而提高了開發效率並降低了出錯的概率。

## 4. 應用層 (Application Layer)

應用層是系統的總指揮，負責管理系統的整體行為、與使用者互動，並提供調試、監控和安全保障等重要功能。系統基於 ESP32 雙核 FreeRTOS，將工作負載嚴格分配到不同的核心與任務中。

### 核心架構：FreeRTOS 多工 + 狀態機驅動的服務集合

系統以 `xTaskCreatePinnedToCore` 將關鍵任務綁定到指定核心：

- **Core 1 (高優先級)**：`Control_Task` — 200Hz 即時控制迴路，負責 IMU 讀取、AHRS 更新、串級 PID 計算、Failsafe 檢查與遙測數據推送。使用 `vTaskDelayUntil` 確保嚴格的週期性執行。
- **Core 0 (低優先級)**：`Comm_Task` — 200Hz 通訊與管理任務，負責序列埠遙測發送、指令接收解析、LED 狀態更新與 OLED 顯示刷新。
- **Core 0 (可選)**：`BT_Task` 或 `Gamepad_Task` — 藍牙遙測或 Bluepad32 手把輸入，透過 `HAS_BT_SERIAL` 編譯旗標在兩種操控模式間切換。

### 關鍵技術演進 (詳細說明)

- **`e9c5ef6` - AppMode 的確立：從混亂到有序**
    在此之前，專案的主循環 (`loop()`) 可能充滿了複雜的 `if-else` 邏輯，各種行為互相交織。此提交透過建立 `AppMode` 類別，正式引入了「有限狀態機」(FSM) 的設計模式，將系統行為抽象為一系列清晰的、互斥的「模式」。這是一次軟體工程上的巨大進步，它為複雜的應用程式行為提供了一個可擴展、可維護的骨架，是系統從一個簡單腳本走向一個健壯應用的里程碑。

- **`7e1ff07` & `e94b63b` - 可交互性的飛躍：打通內外**
    這兩次提交共同構建了一個強大的互動式調試工作流。`7e1ff07` 創建的 `AppScript` 像是為系統打開了一扇「門」，讓外部指令得以進入。而 `e94b63b` 增加的遙測回饋，則像是打開了一扇「窗」，讓內部狀態得以被觀察。兩者結合，徹底改變了開發模式，將傳統「修改-編譯-上傳-觀察」的冗長循環，變革為「即時微調-即時觀察」的高效互動。

- **`5a32ccf` - 斷電記憶的實現：從「實驗品」到「設備」**
    整合 `ConfigStore` 是專案邁向實用化的關鍵一步。它讓耗費大量時間精心調校的 PID 參數得以儲存到非揮發性記憶體(Flash)中。這意味著調校成果不再隨斷電而煙消雲散。系統從一個斷電就需重來的「易失性實驗品」，演變成了一個具有記憶、狀態可複現的「持久化設備」。

- **`c018730` & `6d259b1` - 魯棒性的保障：引入 Failsafe**
    這兩次提交為系統引入了至關重要的「安全意識」。`Failsafe` 模組作為一個獨立的監控者，持續檢查著可能導致危險的系統狀態（如車體傾倒角度過大、感測器斷連）。一旦偵測到異常，它便能果斷介入，切斷馬達輸出，從而保護硬體（電機、齒輪箱）免受損壞，並防止失控的車體造成更大的安全問題。

- **`86cd7db` & `9f5ae51` - 數據可視化：從「感覺」到「看見」**
    `86cd7db` 透過整合藍牙，讓遙測擺脫了 USB 線的束縛，使得在真實運動場景下進行數據記錄和分析成為可能。`9f5ae51` 則極大地豐富了遙測數據包的內容，將 PID 各環節的輸入、輸出、目標值等中間變數全部開放出來。這使得開發者能藉助 VOFA+ 等上位機軟體，將控制器內部的黑盒徹底可視化，讓調優工作從「憑感覺猜」，進化到「看數據分析」。

- **`f5290fb` - 遙測架構的重構：多埠多格式支援**
    此提交對遙測系統進行了根本性的重構。`Telemetry` 類別從單一串口綁定，進化為支援**多埠** (`PORT_USB` / `PORT_BT`) 和**多格式** (`FORMAT_DEFAULT` 感測器原始數據 / `FORMAT_PID` 控制環路詳細數據) 的通用框架。每個遙測實例透過獨立的 FreeRTOS 佇列接收數據，支援動態配置開關、頻率和格式（`set_config`），且資料推送（`push_data`）為非阻塞操作，確保 200Hz 控制迴路永遠不會被串口通訊阻塞。

- **`3fc9bba` - 操控的革新：Bluepad32 手把整合**
    此提交引入了 `HAL_Joystick` 模組，透過 Bluepad32 庫整合了藍牙遊戲手把控制。搖桿以獨立的 FreeRTOS 任務（100Hz）運行在 Core 0 上，透過正規化、死區處理和指令佇列與控制迴路互動。手把按鍵支援即時模式切換（Y=FREE / B=ANGLE / A=REMOTE），搖桿軸支援前進/轉向的類比控制。此功能與傳統的藍牙串口模式互斥，透過 `HAS_BT_SERIAL` 編譯旗標切換。

- **`aaf504d` - 人機介面的升級：SPI OLED 顯示器與自動啟停**
    此提交同時引入了兩項面向實用性的重大功能。**SPI OLED 顯示器** (`HAL_Display`) 透過 Software SPI 驅動 128x32 SSD1306 螢幕，以分髒標記 (Dirty Flag) 機制僅在狀態變化時重繪，實時顯示當前模式、待選模式、電池電壓和延遲計數。**自動啟停機制** (`check_auto_start_stop`) 實現了兩個智能行為：1）**懸空保護 (Pick-up Detection)**：當車體姿態接近直立但馬達高速空轉超過 500ms 時，判定車體被撿起，自動切入 `MODE_FREE` 保護；2）**落地啟動 (Drop-to-Start)**：當車體處於 `MODE_FREE` 且姿態回到直立穩定狀態超過 500ms 時，自動恢復到 `pending_mode`，實現「放下即跑」的無縫操作體驗。

- **`61b0832` - 安全架構的解耦：Failsafe 回調機制與電池監控**
    此提交是應用層架構上的一次重要精煉。Failsafe 類別原本直接依賴 `AppMode` 來切換模式，造成了模組間的緊耦合。現在，Failsafe 改為接受一個**函式指標回調** (`set_pending_mode_fn`)，透過回調間接通知 `AppMode` 設定待選模式。這使得 `Failsafe` 完全不需要知道 `AppMode` 的存在，實現了真正的模組解耦。同時，此提交也整合了 `HAL_Battery` 電池電壓監控模組，透過 ADC 讀取 GPIO 35 的分壓值並以低通濾波穩定化，將電池狀態納入遙測數據和 OLED 顯示中，為低電量保護等未來功能奠定了基礎。

- **輪胎選模式 (`update_mode_selection`)：物理世界的 UI**
    在 `MODE_FREE` 狀態下，系統會監測右輪的 PCNT（脈衝計數器）累積值。當使用者用手轉動右輪超過每 60 度一個檔位時，`pending_mode` 會在 `MODE_ANGLE` ~ `MODE_REMOTE` 之間循環切換，並即時反映在 OLED 螢幕上。這是一個將「馬達編碼器」重新利用為「物理旋鈕」的巧妙設計，讓使用者在沒有手把或電腦的情況下，僅靠車體本身就能選擇運行模式。

### 重要設計資產

1. **中心化的狀態機管理 (`AppMode`)**：
    - **資產說明**：一個實現了有限狀態機 (FSM) 的 `AppMode` 類別。它定義了系統所有可能的工作模式 (`Mode_t`：STOP / FREE / PWM / MOTOR / ANGLE / VELOCITY / REMOTE / TURBO)，並包含了一套嚴格的規則來管理模式之間的切換。
    - **解決問題**：解決了使用大量 `if-else` 或全域旗標來管理狀態時，容易出現的「狀態混亂」和「行為衝突」問題。例如，錯誤的狀態管理可能導致系統在「已跌倒」模式下，仍然嘗試執行「平衡」的邏輯。
    - **技術價值**：FSM 確保了系統在任何時刻都**有且僅有**一個清晰的、預定義的狀態。它為每個狀態提供了明確的入口、出口和執行邏輯，例如在切換模式時自動重置所有 PID 的積分器和濾波器（`reset_control_state()`）。搭配 `pending_mode` 機制和 3 秒安全延遲，使得模式切換既安全又可預測。

2. **即時遙測與線上調參工作流**：
    - **資產說明**：由 `app_script`（接收指令）、`hal_telemetry`（發送數據）和上位機軟體（如 VOFA+）協同構成的一整個開發工作流。支援 USB 和藍牙雙通道，以及 `FORMAT_DEFAULT`（感測器數據）和 `FORMAT_PID`（控制環路數據）兩種遙測格式。
    - **解決問題**：它徹底解決了嵌入式，特別是控制系統開發中的「黑盒調試」難題。在沒有這個工作流時，PID 調參是一個極其痛苦和低效的「猜測-編譯-燒錄-觀察」的循環。
    - **技術價值**：這個資產組合為開發者提供了一個強大的「白盒儀表盤」。開發者可以**在系統不中斷運行的情況下**，即時觀測任意內部變數（如 PID 的 P/I/D 各項輸出）的波形，並透過序列埠指令**即時修改** PID 增益。遙測系統的非阻塞佇列設計確保即使串口緩慢，也不會影響 200Hz 控制迴路的即時性。

3. **系統魯棒性保障 (Failsafe & ConfigStore & Battery)**：
    - **資產說明**：一個由「安全衛士」(`Failsafe`)、「記憶管家」(`ConfigStore`) 和「電量監視」(`HAL_Battery`) 組成的健壯性保障體系。Failsafe 透過回調函式解耦，持續監控迴圈性能（`FS_ERROR_LOOP_SLOW`）、AHRS 就緒狀態（`FS_ERROR_AHRS_UNREADY`）、和臨界傾角（`FS_ERROR_CRITICAL_ANGLE`），並透過 LED 狀態指示（`ARMED` / `INITIALIZING` / `DISARMED`）提供即時的視覺回饋。
    - **解決問題**：1. 硬體在極端情況下（如摔倒、馬達堵轉）的物理損壞。 2. 軟體配置（如調參成果）在斷電後的數據丟失。 3. 電池電量耗盡導致的行為異常。
    - **技術價值**：`Failsafe` 透過回調機制（`set_pending_mode_fn`）提供**硬體層面的保護**，且完全不依賴 `AppMode`，實現了真正的模組解耦。`ConfigStore` 提供**軟體層面的保護**，尊重並保留了開發者的勞動成果。`HAL_Battery` 透過 ADC 低通濾波持續監測電池電壓，為未來的低電量自動降級或關機提供了數據基礎。三者共同作用，讓系統從一個脆弱的實驗原型，蛻變為一個可以在真實世界中可靠、安全地反覆使用的健壯設備。

4. **多模態人機交互體系**：
    - **資產說明**：由 OLED 顯示器（`HAL_Display`，SPI 驅動，分髒標記刷新）、LED 狀態指示燈（`HAL_LED`，三態閃爍模式）、藍牙遊戲手把（`HAL_Joystick`，Bluepad32 驅動）和輪胎物理選模式（`update_mode_selection`，PCNT 旋鈕）共同組成的多層次人機交互體系。
    - **解決問題**：早期系統缺乏直觀的狀態回饋和便捷的操控方式，使用者必須依賴 USB 串口才能了解系統狀態和發送指令。
    - **技術價值**：OLED 顯示器即時顯示當前模式、待選模式和電池電壓，讓使用者「一眼就知道系統在幹什麼」。藍牙手把提供了無線的類比控制，搭配按鍵模式切換，實現了專業級的遙控體驗。而輪胎選模式機制則讓系統在完全脫離外部設備的情況下，僅靠轉動輪胎就能切換工作模式，實現了真正的「獨立運作」。

### 未使用腳位 (Unused / Available)

以下腳位目前未分配功能，可供未來硬體擴充（如超音波、雷射雷達或感測器）使用：

- **通用輸出入 (GPIO)**: 無 (常用腳位已全數分配)
- **僅限輸入 (Input Only)**: 36 (VP), 39 (VN)
- **不可使用 (Internal Flash)**: GPIO 6, 7, 8, 9, 10, 11 (系統內部 Flash 佔用，嚴禁使用)

> [!IMPORTANT]
> 在擴充使用 GPIO 0, 2, 5, 12, 15 時需注意其 Strapping Pins 特性，可能會影響 ESP32 的開機模式。目前配置已避開衝突或已適當處理。
